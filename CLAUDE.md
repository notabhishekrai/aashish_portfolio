# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Plain-PHP (no framework, no Composer, no build step) portfolio site for Aashish Rai, scaffolded to deploy on Hostinger shared hosting. Content is database-backed (MySQL via PDO) and editable through a plain-PHP admin panel at `/admin/` — see `README.md`'s "Database Setup" and "Admin panel" sections for one-time setup.

## Commands

```bash
cp .env.example .env                    # first-time local setup
php -S localhost:8000 -t .              # run locally at http://localhost:8000
php -l path/to/file.php                 # lint a single file before committing
find . -name "*.php" -exec php -l {} \; # lint everything
```

There is no test suite, linter config, or build step beyond `php -l`.

## Architecture

- **The repo root is the web root.** Hostinger's Git auto-deploy clones the whole repo into one directory (`public_html`), so there's no separate `public_html/` subfolder in this repo — `index.php`, `config/`, `includes/`, `assets/`, `.htaccess` all sit at the top level and get deployed as-is. Don't reintroduce a nested `public_html/` folder.
- **`config/` and `includes/` are each protected by their own `.htaccess`** (`Require all denied` / `Deny from all`, both syntaxes for Apache 2.2 and 2.4+/LiteSpeed compatibility) rather than by living outside the web root — Git-based single-directory deploy can't split files across two locations the way manual FTP upload could. `includes/*.php` are partial templates that assume `config.php`/`functions.php` already ran, so requesting them directly fatal-errors; block, don't fix that. `.env` is protected by the dotfile-deny `FilesMatch` rule in the root `.htaccess`, plus an explicit `.git/` block since some deploy setups leave `.git` inside the served directory.
- **`config/config.php`** is the entry point every page requires first, via `require_once __DIR__ . '/config/config.php'`. It hand-rolls a `.env` parser (`load_env()`) instead of using a Composer dotenv package — this project has no `vendor/`. It also defines `APP_ENV`/`SITE_NAME` and sets the error-display mode. `error_reporting` is always `E_ALL` regardless of environment — only `display_errors` toggles, so production issues still get logged, just not shown to visitors. Public pages carry no session (`session_start()` is called nowhere except `admin/includes/bootstrap.php`, scoped to the admin panel only).
- **`config/database.php`** exposes `get_db(): PDO`, a lazily-instantiated singleton (static var inside the function) built from `DB_*` env vars. In production it swallows `PDOException` and dies with a generic message rather than leaking connection details; in non-production `APP_ENV` it rethrows.
- **`database/schema.sql`** is the entire schema plus seed data, hand-written since there's no migration tooling — applied once, manually, via phpMyAdmin (same one-time-manual-step pattern as creating `.env`; see README). `database/` is protected by its own deny-all `.htaccess`, same as `config/`/`includes/`.
- **Page structure**: each `*.php` page at the repo root requires `config/config.php`, `includes/functions.php`, and `includes/content.php`, then `includes/header.php`, then its own markup, then `includes/footer.php`. `header.php` reads two optional variables set by the page *before* it's included — `$pageTitle` and `$pageDescription` — to fill in `<title>` and the meta description; see `index.php` for the pattern.
- **`includes/functions.php`** holds two small helpers used throughout: `e($string)` (htmlspecialchars wrapper — always escape interpolated content) and `asset_url($path)` (prefixes `/assets/`).
- **`includes/content.php`** is the read-only DB access layer public pages use: `get_section($page, $section)` returns a page/section's scalar fields (shaped exactly like the old hardcoded `$hero`/`$about`/`$contact` arrays), `get_stats()`/`get_services()`/`get_socials()`/`get_nav_links()` return small ordered collections, and `get_featured_work()`/`get_all_work()`/`get_work_by_slug()`/`get_next_work()` (plus the `_journal` equivalents) drive the work/journal archive and detail pages. `img_or_placeholder($path, $text, ...)` renders a real `<img>` when a path is set or falls back to the original `<div class="img-placeholder grayscale">` markup otherwise — every image slot on the site goes through it.
- **Content-as-data pattern, now DB-backed**: content still reaches templates as plain PHP arrays shaped like `$hero`/`$about`/`$services`/`$work`/`$journal`/`$contact` — but those arrays are now fetched from the database via `includes/content.php` rather than hardcoded. The `foreach`-over-array rendering pattern in each page is unchanged; only the array's source changed. New sections should still follow this array-then-loop shape, backed by a `site_settings` row (see below) or a small dedicated table if it's a repeating collection.
- **Database schema shape**: `site_settings` is a generic `(page, section, field_key, field_value)` key-value table for singleton scalar fields (hero copy, about paragraphs, contact info, nav/footer labels). `stats`, `services`, `socials`, and `nav_links` are small dedicated tables for repeating collections the admin adds/removes as independent rows. `work_projects` and `journal_entries` are the two "detail template" entities — real columns plus JSON columns (`tags`, `credits`, `stills`, the various `*_paragraphs` fields) for bounded substructure that's always read/written as a whole. `contact_submissions` and `admin_users` round it out. No foreign keys — nothing needs referential integrity beyond the declared `UNIQUE`s.
- **Image placeholders with a real-image fallback**: every image slot renders through `img_or_placeholder()` (see above) — a `<div class="img-placeholder grayscale">` (see `assets/css/style.css`) until a real photo is uploaded through the admin, then a real `<img class="... grayscale">` automatically. Don't hand-edit placeholder markup directly in a page file; it all flows through that one helper now.
- **Pages**: `index.php` (home), `work-archive.php`, `work-detail.php` (slug-routed, `?slug=<slug>`, one shared template for every work project — looked up via `get_work_by_slug()`, 404s via `404.php` on an unknown slug), `journal-archive.php`, `journal-detail.php` (same pattern, `?slug=<slug>` via `get_journal_by_slug()`; the `?entry=N` query param from the pre-CMS version is gone).
- **`admin/`** is the CMS admin panel — plain server-rendered PHP + vanilla JS (`assets/js/admin.js`, `assets/css/admin.css`), no framework. Unlike `config/`/`includes/`/`database/`, it is **not** `.htaccess`-blocked — admin pages must be directly requestable — so protection is PHP-level session auth (`admin/includes/auth.php`'s `require_login()`) instead. Every admin page follows `bootstrap.php` (config/db/session) → `auth.php` (`require_login()`) → `csrf.php` (CSRF token on every POST form). Image uploads go through `admin/includes/upload.php`, which validates via `finfo` MIME sniffing (not client-supplied type), re-derives the extension from the detected MIME, and writes randomized filenames into `assets/images/uploads/` (not committed — see `.gitignore`; protected against script execution by its own `.htaccess`, but still publicly GET-able).
- **Contact form**: `index.php`'s form posts to `contact-submit.php` (root-level, public, POST-only), which validates and inserts into `contact_submissions`, then redirects back with `?contact=sent` or `?contact=error`. It uses a honeypot field instead of CSRF (anonymous form, no session, nothing privileged to forge). No outgoing email — check `/admin/contact-submissions.php`.

## Development Workflow

- **Branch per change**: `feature/<short-name>` for new pages/sections, `fix/<short-name>` for bugs. Don't commit straight to `main`.
- **Commits**: focused, one logical change each. Message explains *why*, not just what changed (e.g. `Add contact form validation` not `update index.php`). Follow conventional-commit-style prefixes where it reads naturally (`feat:`, `fix:`, `chore:`) but don't force it if a plain sentence is clearer.
- **Never commit `.env`** or anything under `config/` that contains real credentials — `.gitignore` already excludes `.env`; double-check `git status` before committing if you touched `config/`.
- **Lint before committing**: run `php -l` on every changed `.php` file — there's no CI yet to catch a syntax error.
- **PR-based review**: push the branch, open a PR against `main`, merge only after review — even solo, this keeps `main` deployable at all times since Hostinger's Git auto-deploy pushes whatever's on `main` straight to production.
- **Deploying**: `main` is the deployable branch. Hostinger's Git auto-deploy (hPanel > Websites > Manage > Advanced > Git) is connected to this repo with deploy Directory set to `public_html` — merging to `main` deploys automatically. `.env` isn't part of the repo; it's created once directly on the server via File Manager with real credentials. See `README.md` for details.
